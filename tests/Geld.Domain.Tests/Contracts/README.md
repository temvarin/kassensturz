# Contracts

Data that one version of the app writes and another version reads. Its shapes are the records in `src/Geld.Domain/Contracts`, which map to the domain model; the model itself knows no JSON. Each file here is a sample of what a released version actually wrote: the historical ones were generated by checking out the released commit and running its code. `ContractTests` checks them on every build.

| Contract | Written by | Read by | Version | Rule for samples of an older version |
|---|---|---|---|---|
| `local` (`geld.data` in localStorage) | app | the next version, or the previous one after a rollback | local schema | loads through a migration |
| `backup` (the backup file) | app | any later version, years later | backup schema | loads through a migration |
| `sync-request` | app | server | protocol | read far enough for the server to answer 409, not 400 |
| `sync-response` | server | app | protocol | none: the server answers only apps of its own protocol |
| `document-kindergeld`, `document-budget` (rows in `dbo.Documents`, written with `DocumentJson`) | server | server, and `db/restore.sql` | protocol | read without losing anything: rows and their 6-month history are never migrated |
| `whoami` | server | app | protocol | read without losing anything: an old app reads what a new server answers |

## The two checks

- **This version writes exactly the newest sample** of each contract. A shape change fails the build until someone decides it on purpose.
- **Every sample stays readable.** A sample of the current version must read without losing a value: everything in it is still there after reading it into the domain model and writing it again, as the app and the server do. New properties may appear, and a null may become a missing property. Samples of older versions follow the rule in the table.

## When the write check fails

1. Decide whether the change is intended. A renamed or removed property, or a changed type, breaks the samples of the current version: then raise the schema of that contract (and add a migration to `Storage/DataStore`) or the protocol (`SyncRequestJson.CurrentProtocol`). An added optional property needs neither, except in an item or in the settings of a synced document: those travel whole, so an older app would send them without it, and that needs a new protocol.
   - The stored data and backup files have a schema each (`DataStore.LocalSchema`, `DataStore.BackupSchema`): raise only the one whose shape changed, so backup files stay readable by older versions as long as possible.
   - Raising the protocol fails the write check of every API contract, also those whose shape is unchanged: their newest sample must carry the new version. Copy them as they are.
2. Copy the `received.json` that the failing test names into this contract's folder as `v<version>-<release date>.json`.

Never edit or delete a sample: it stands for data that exists on phones, in backup files and in the database.

## Known warts, kept as they are

- The serialized changes carry computed `isEmpty` properties. Readers ignore them. The contract records keep writing them (`SyncJson.cs`).
- The sync JSON writes nulls (`"note": null`), but the stored data leaves them out: the same records go through two serializers with different settings.
